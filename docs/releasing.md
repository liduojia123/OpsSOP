# 版本交付与维护

OpsSOP 以带版本号的源码发行交付，应用与数据库由部署方自托管。`v3.6.2` 对应产品版本 `3.6.2`；Git tag 标识具体源码，部署时固定 tag 或提交，不直接跟随移动中的主分支。

## 交付清单

| 交付项 | 位置 |
|---|---|
| 产品版本与功能变化 | `VERSION`、`CHANGELOG.md`、GitHub Releases |
| 应用源码与数据库迁移 | `frontend/`、`backend/app/`、`backend/alembic/` |
| 部署配置 | Compose 文件、`.env.example`、`.env.production.example` |
| 使用与维护 | `docs/` |
| 质量工具 | 后端与前端测试、业务闭环脚本、版本化合成评测集 |
| 许可与反馈 | `LICENSE`、`THIRD_PARTY_NOTICES.md`、`SECURITY.md` |

真实密钥、业务数据、数据库备份、依赖缓存和内部审查记录不属于公开发行内容。

## 部署交接

1. 确认使用的 Git tag、数据库位置、域名和应用入口，按部署文档准备独立配置。
2. 设置管理员和随机凭据，关闭演示种子；按需配置聊天与 embedding 服务及数据外发范围。
3. 按生产 Compose 启动应用，完成管理员登录、角色分配和基础分类设置。
4. 约定备份目录、访问权限、保留方式、恢复目标和负责人员；首次业务录入前建立备份流程。
5. 向使用人员交接故障处理、人工确认、审核发布与知识反馈流程。

正式业务环境的网络、数据和模型配置由部署方确认。源码发行不代表目标环境已完成部署验收，也不附带固定业务准确率或可用性承诺。

## 升级与回退

升级前阅读版本记录并备份数据库，保留旧版源码或镜像、旧配置及备份元信息。选择明确的目标 tag，构建和重建应用；保留现有 Compose 项目名与命名卷，防止接入错误数据库。

数据库迁移与应用版本分别处理。出现问题时，先停止新业务写入，再按备份恢复流程恢复到新库并切换对应版本；不能仅凭应用镜像回退推定数据库已经回退。操作步骤见[部署指南](deployment.md)和[备份恢复](backup-restore.md)。

## 维护与支持

功能问题通过 GitHub Issue 记录版本、复现、影响及脱敏日志。安全问题使用私密渠道。公开仓库不提供默认商业服务合同、托管 SLA 或自动容灾；如需这些服务，应另行约定实施范围、响应方式及交付责任。

维护发行时更新版本记录，说明数据兼容性和配置变化，保留许可证与第三方声明。测试、评测和演练结果只记录真实执行的环境与范围。
